# MCP Roadmap 2026 (миграция текущего решения → MCP)

## Цель года

Перевести текущий продукт (генератор + переводчик + проверка/улучшение README + регенерация) в **MCP-совместимую платформу инструментов**, где:

- правки README делаются **точечно** (патчи, блоки), а не “перегенерация всего”;
- можно добавлять новые инструменты без переписывания ядра;
- есть **dev/staging/prod окружения**, наблюдаемость, безопасность и процессы релиза;
- качество контролируется **регрессионными метриками** + эталонными кейсами + экспертным фидбеком.

## Почему начинаем с инфраструктуры

Сейчас всё локально на одной машине → это главный риск:

- нет воспроизводимости окружения;
- нет staging для безопасных экспериментов;
- тяжело подключать людей (совместная разработка/доступы/секреты);
- любые “агентные” интеграции будут нестабильны.

Поэтому в roadmap сначала: минимальный dev сервер (VPS/VM) + контейнеризация + секреты + базовый CI.

## Что считаем “MCP переходом”

### 1) MCP Server (один, много tools)

Обычно достаточно **одного MCP server** “Content Tools”, который экспортирует tools:

- генерация проекта
- перевод
- проверка README
- улучшение/регенерация
- document tools: список защищённых блоков, удаление формул, перефразирование фрагмента, регенерация секции

### 2) Контракты инструментов

Для каждого tool фиксируем:

- JSON schema входа/выхода
- ошибки/коды
- ограничения (время/токены/размер документа)
- идемпотентность
- обязательные поля трассировки (`request_id`, `user_id`, `trace_id`)

### 3) Document Editing слой

Критично для качества и “не ломать структуру”:

- protected blocks (формулы/mermaid/код) → маркеры `[[[BLOCK_N]]]`
- LLM-редактирование только через **patches** (`old_text` → `new_text`)
- версионирование README (document_id/version_id)

## Роли и минимальная команда (прагматично)

Если вы одна/один — roadmap всё равно полезен как список этапов. Если подключаем людей:

- **Tech Lead/Архитектор (0.2–0.5 FTE)**: контракты, архитектура, качества и риски.
- **Backend (0.7–1.0 FTE)**: MCP tools, document service, API, очередь.
- **DevOps (0.3–0.7 FTE)**: dev/staging/prod, мониторинг, бэкапы, секреты.
- **DS/LLM Engineer (0.8–1.2 FTE)**: eval harness, политики/guardrails, контекст учебного плана.
- **Эксперт предметной области (0.2–0.5 FTE)**: эталонные кейсы и критерии “как у эксперта”.
- **PM (0.2–0.5 FTE)**: beta rollout, сбор фидбека, приоритизация.

## Инфраструктура (минимум, без “энтерпрайза”)

- Dev VPS/VM: Docker Compose (API+DB+Redis+MinIO), доступ по SSH/VPN.
- Staging VPS/VM: отдельные ключи LLM и отдельные данные.
- Prod VPS/VM: бэкапы Postgres/MinIO, мониторинг, runbooks.
