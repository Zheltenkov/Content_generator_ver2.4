# Критерии Валидации Контента

## Обзор

Система критериев валидации Content Generator проверяет сгенерированный контент по 39 критериям, разделённым на 4 основных раздела. Каждый критерий оценивается бинарно (0 или 1) и может использовать различные методы проверки: скриптовый анализ, AI-агенты, семантический анализ (SBERT) или их комбинацию.

## Архитектура системы критериев

### Общая структура

```
┌─────────────────────────────────────────────────────────────────┐
│              CRITERIA VALIDATION SYSTEM                         │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                    RUBRIC SCORER                                │
│  (validators/rubric/scorer.py)                                  │
│                                                                 │
│  - Координирует проверку всех критериев                         │
│  - Параллельное выполнение разделов                             │
│  - Кэширование результатов                                      │
│  - Формирование итогового отчёта                                │
└─────────────────────────────────────────────────────────────────┘
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ Section 1    │   │ Section 2    │   │ Section 3    │
│ Checker      │   │ Checker      │   │ Checker      │
│              │   │              │   │              │
│ Структура    │   │ Требования   │   │ Сторителлинг │
│ (1.1-1.6)    │   │ (2.1-2.5)    │   │ (3.1-3.2)    │
└──────────────┘   └──────────────┘   └──────────────┘
        │                   │                   │
        └───────────────────┼───────────────────┘
                            │
                            ▼
                   ┌──────────────┐
                   │ Section 4    │
                   │ Checker      │
                   │              │
                   │ Tone & Edit  │
                   │ (4.1-4.3)    │
                   └──────────────┘
```

### Модели данных

```
┌─────────────────────────────────────────────────────────────┐
│                    CRITERIA MODELS                          │
└─────────────────────────────────────────────────────────────┘

CriteriaItem
    │
    ├─── id: str                    # "1.1", "2.1.1", etc.
    ├─── title: str                 # Название критерия
    ├─── description: str            # Описание требования
    ├─── check_method: CheckMethod   # Метод проверки
    │    ├─── SCRIPT                # Regex, парсинг
    │    ├─── AI_AGENT              # LLM проверка
    │    ├─── SBERT                 # Семантический анализ
    │    └─── HYBRID                # Комбинация методов
    ├─── score: int                 # 0 или 1
    ├─── comments: List[str]        # Комментарии/предупреждения
    ├─── details: Dict[str, Any]    # Детальная информация
    ├─── parent_id: Optional[str]    # ID родителя (для группировки)
    └─── strictness: StrictnessLevel
         ├─── HARD                  # Блокирует прохождение
         └─── SOFT                  # Рекомендация

CriteriaReport
    │
    ├─── items: List[CriteriaItem]                # Все 39 критериев
    ├─── total: int                               # Сумма баллов
    ├─── max_score: int                           # Максимум (39)
    └─── summary: Dict[str, int]                  # Сводка по разделам
         └─── {"1": 5, "2": 12, "3": 2, "4": 3}
```

## Раздел 1: Соответствие шаблону структуры

**Checker:** `Section1Checker`  
**Критериев:** 6 (1.1-1.6)  
**Метод:** SCRIPT (regex, парсинг)

### Структура раздела 1

```
┌─────────────────────────────────────────────────────────────┐
│              SECTION 1: STRUCTURE TEMPLATE                    │
└─────────────────────────────────────────────────────────────┘

1.1: Проверка наличия блока с названием
     ├─── Метод: SCRIPT
     ├─── Проверка: H1 в первой строке (#)
     └─── Строгость: HARD

1.2: Проверка наличия блока с аннотацией
     ├─── Метод: SCRIPT
     ├─── Проверка: Текст после H1 без заголовков/маркеров
     └─── Строгость: HARD

1.3: Проверка наличия блока с оглавлением
     ├─── Метод: SCRIPT
     ├─── Проверка: ## Содержание/Оглавление + ≥3 строки
     └─── Строгость: HARD

1.4: Проверка наличия блока с введением и инструкцией
     ├─── Метод: SCRIPT
     ├─── Проверка: ## Глава 1 + не пустой блок (>50 символов)
     └─── Строгость: HARD

1.5: Проверка наличия теоретического блока
     ├─── Метод: SCRIPT
     ├─── Проверка: ## Глава 2 + не пустой блок (>50 символов)
     └─── Строгость: HARD

1.6: Проверка наличия практического блока
     ├─── Метод: SCRIPT
     ├─── Проверка: ## Глава 3 + не пустой блок (>50 символов)
     └─── Строгость: HARD
```

### Процесс проверки

```
┌─────────────────────────────────────────────────────────────┐
│              SECTION 1 CHECK PROCESS                         │
└─────────────────────────────────────────────────────────────┘

Section1Checker.check(md)
    │
    ├─── 1.1: Поиск H1
    │    ├─── rx_h1.search(md)
    │    └─── Проверка: md.strip().startswith('#')
    │
    ├─── 1.2: Извлечение аннотации
    │    ├─── Текст между H1 и первым H2
    │    ├─── Проверка: нет заголовков, нет маркеров списков
    │    └─── Проверка: не пустой
    │
    ├─── 1.3: Поиск оглавления
    │    ├─── rx_toc.search(md)
    │    ├─── Извлечение блока до следующего H2
    │    └─── Проверка: ≥3 строки
    │
    ├─── 1.4: Поиск Главы 1
    │    ├─── rx_chapter1.search(md)
    │    ├─── Извлечение контента
    │    └─── Проверка: длина > 50 символов
    │
    ├─── 1.5: Поиск Главы 2
    │    ├─── rx_chapter2.search(md)
    │    ├─── Извлечение контента
    │    └─── Проверка: длина > 50 символов
    │
    └─── 1.6: Поиск Главы 3
         ├─── rx_chapter3.search(md)
         ├─── Извлечение контента
         └─── Проверка: длина > 50 символов
```

### Детали подкритериев

#### 2.1: Аннотация

```
┌─────────────────────────────────────────────────────────────┐
│                    ANNOTATION CHECKING                         │
└─────────────────────────────────────────────────────────────┘

AnnotationChecker.check(annotation, title, theory_text)
    │
    ├─── 2.1.1: Длина аннотации
    │    ├─── count_chars(annotation)
    │    └─── Проверка: 300 ≤ length ≤ 800
    │
    ├─── 2.1.2: Структура аннотации
    │    │
    │    ├─── [Если LLM доступен]
    │    │    └─── _ai_check_annotation_structure()
    │    │         ├─── LLM проверяет 3 элемента:
    │    │         │    ├─── has_purpose: назначение проекта
    │    │         │    ├─── has_content: краткое описание
    │    │         │    └─── has_outcome: ожидаемый результат
    │    │         └─── score = 1 если ≥2 элемента найдено
    │    │
    │    └─── [Fallback: ключевые слова]
    │         ├─── Поиск паттернов в тексте
    │         └─── score = 1 если ≥2 паттерна найдено
    │
    └─── 2.1.3: Соответствие теме проекта
         │
         ├─── Специальные случаи:
         │    ├─── is_formal_title(title) → score = 1 (SOFT)
         │    └─── is_generic_title(title) → score = 1 (SOFT)
         │
         ├─── [Если SBERT доступен]
         │    ├─── similarity_annotation = SBERT(title, annotation_focus)
         │    ├─── similarity_theory = SBERT(title, theory_summary)
         │    ├─── similarity = max(similarity_annotation, similarity_theory)
         │    │
         │    ├─── Если similarity >= 0.22 → score = 1 (SBERT)
         │    ├─── Если 0.12 <= similarity < 0.22 → LLM проверка (HYBRID)
         │    └─── Если similarity < 0.12 → score = 0 (SBERT)
         │
         └─── [Fallback без SBERT]
              └─── score = 1 (SOFT, с предупреждением)
```

#### 2.2: Оглавление

    │    ├─── Нормализация якорей
    │    └─── Проверка: заголовок существует в тексте
    │
    ├─── 2.2.3: Согласованность названий
    │    ├─── Извлечение текстов ссылок из TOC
    │    ├─── Нормализация (убрать дефисы, пробелы)
    │    └─── Поиск соответствия в заголовках H2/H3
    │
    └─── 2.2.4: Смысловая точность заголовков
         │
         ├─── Для каждого заголовка (до 5):
         │    │
         │    ├─── Нормализация заголовка
         │    │    └─── Убрать "Глава N.", "Часть N."
         │    │
         │    ├─── Поиск раздела в тексте

### SBERT (Семантический анализ)

```
┌─────────────────────────────────────────────────────────────┐
│                    SBERT METHOD                               │
└─────────────────────────────────────────────────────────────┘

Используется для:
    ├─── Семантическое сходство текстов
    ├─── Проверка соответствия темам
    └─── Анализ когерентности

Процесс:
    ├─── Создание эмбеддингов
    │    ├─── embedding_function(text1)
    │    └─── embedding_function(text2)
    │
    ├─── Вычисление cosine similarity
    │    └─── similarity = cosine(emb1, emb2)
    │
    └─── Сравнение с порогом

Пороги:
    ├─── 2.1.3: 0.22 (уверенно ок), 0.12 (зона LLM)
    ├─── 2.5.7: 0.40 (связь теории и практики)
    └─── 3.1: 0.5 (когерентность между абзацами)

Примеры:
    ├─── 2.1.3: Аннотация vs название проекта
    ├─── 2.5.7: Теория vs практика
    └─── 3.1: Соседние абзацы
```

### HYBRID (Комбинация методов)

```
┌─────────────────────────────────────────────────────────────┐
│                    HYBRID METHOD                              │
└─────────────────────────────────────────────────────────────┘

Используется для:
    └─── Комбинация SBERT + AI_AGENT

Процесс:
    ├─── Шаг 1: SBERT проверка
    │    ├─── Вычисление similarity
    │    ├─── Если >= high_threshold → score = 1 (SBERT)
    │    └─── Если < low_threshold → score = 0 (SBERT)
    │
    └─── Шаг 2: LLM проверка (если в зоне неопределённости)
         ├─── Если low_threshold <= similarity < high_threshold
         ├─── LLM анализ с контекстом similarity
         └─── Результат: score на основе LLM

Примеры:
    ├─── 2.1.3: Аннотация vs название (SBERT + LLM)
    └─── 2.2.4: Точность заголовков (SBERT + LLM)
```

## Процесс выполнения проверки

### Полный цикл RubricScorer

```
┌─────────────────────────────────────────────────────────────┐
│              RUBRIC SCORER EXECUTION                          │
└─────────────────────────────────────────────────────────────┘

RubricScorer.score(md, learning_outcomes, use_cache)
    │
    ├─── Проверка кэша
    │    └─── Если use_cache и результат в кэше → возврат
    │
    ├─── Параллельное выполнение разделов
    │    │
    │    ├─── ThreadPoolExecutor(max_workers=4)
    │    │
    │    ├─── Section 1: Section1Checker.check(md)
    │    │    └─── 6 критериев (1.1-1.6)
    │    │
    │    ├─── Section 2: Section2Checker.check(md, learning_outcomes)
    │    │    └─── 26 критериев (2.1-2.5)
    │    │
    │    ├─── Section 3: Section3Checker.check(md)
    │    │    └─── 2 критерия (3.1-3.2)
    │    │
    │    └─── Section 4: Section4Checker.check(md)
    │         └─── 3 критерия (4.1-4.3)
    │
    ├─── Сбор результатов
    │    ├─── items.extend(section1_items)
    │    ├─── items.extend(section2_items)
    │    ├─── items.extend(section3_items)
    │    └─── items.extend(section4_items)
    │
    ├─── Подсчёт итогов
    │    ├─── total = sum(item.score for item in items)
    │    ├─── max_score = len(items)  # Должно быть 39
    │    └─── summary = группировка по разделам
    │
    ├─── Сохранение в кэш (если use_cache)
    │
    └─── Возврат: CriteriaReport(items, total, max_score, summary)
```

### Параллелизация

```
┌─────────────────────────────────────────────────────────────┐
│              PARALLELIZATION STRATEGY                        │
└─────────────────────────────────────────────────────────────┘

Уровень 1: Разделы (независимые)
    ├─── Section 1, 2, 3, 4 выполняются параллельно
    └─── ThreadPoolExecutor(max_workers=4)

Уровень 2: Подкритерии раздела 2 (независимые)
    ├─── 2.1, 2.2, 2.3, 2.4, 2.5 выполняются параллельно
    └─── ThreadPoolExecutor(max_workers=5)

Уровень 3: Внутри подкритериев (если возможно)
    └─── Batch embedding для SBERT
```

## Кэширование

### Validation Cache

```
┌─────────────────────────────────────────────────────────────┐
│                    VALIDATION CACHE                           │
└─────────────────────────────────────────────────────────────┘

Использование:
    ├─── Ключ: markdown текст (хеш)
    ├─── Значение: CriteriaReport
    └─── Цель: Избежать повторных проверок

Процесс:
    ├─── get_cache() → ValidationCache
    ├─── cache.get(md) → CriteriaReport | None
    └─── cache.set(md, report) → сохранение

Преимущества:
    ├─── Ускорение повторных проверок
    ├─── Экономия LLM вызовов
    └─── Экономия SBERT вычислений
```

## Best Practices

1. **Параллелизация**: Независимые проверки выполняются параллельно
2. **Кэширование**: Результаты кэшируются для повторных проверок
3. **Fallback стратегии**: Если LLM/SBERT недоступен, используется SCRIPT
4. **Толерантность**: SOFT критерии не блокируют прохождение
5. **Детализация**: Каждый критерий содержит details для отладки
6. **Логирование**: Все шаги логируются для трассировки
